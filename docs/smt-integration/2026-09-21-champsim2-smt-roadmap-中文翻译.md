## 标题与范围

**原文**：日期 2026-09-21。状态：基于源码的侦察 + 提议的开发阶段，没有实现任何代码。**用户选定「多条相互独立的 trace 共享一个物理核」作为第一个里程碑**。每条 trace 最初代表一个独立的地址空间。协作线程、共享内存同步、迁移、OS 调度，都放到以后。

## 证据与范围

**原文**：两个独立侦察员分别查了 Sniper、Scarab，一个协调 agent 对照了 ChampSim2 的接口。三个仓库都没有 `.codegraph/` 目录，所以直接搜源码、读源码。检查的是特定版本（列了一张表），结果：Sniper 在 ROB 模型里有真 SMT；Scarab 这个版本没有 SMT；ChampSim2 一条指令流一个核，有若干「身份和所有权」假设必须拆开。结论都来自读代码，不是跑实验。

💡理解：这段在交代「我这些结论哪来的」——**都是读对方源码读出来的，不是瞎猜**，还标了版本号，方便你复现。

## 参考模拟器到底提供了什么

### Sniper：借它的「所有权模型」和「明确仲裁」

**原文**：Sniper 模拟一个物理核里有多个逻辑上下文，共享一个 `RobSmtTimer`（计时器）。每个 `RobThread` 拥有自己的 ROB 队列、依赖追踪器、前端暂停状态、计数器；计时器拥有核时钟、发射竞争模型、RS 占用、load/store 竞争模型。

几个独立选择的策略：
- **发射（dispatch）**：每拍选**一个**有资格的上下文，用轮转优先级——不是给每个上下文都发一份发射预算。
- **issue**：`simultaneous_issue=true` 时一周期内可访问多个上下文，执行竞争是共享的。
- **ROB**：每上下文一个队列，用「总窗口分配」策略；多个 deque 不等于多个满容量的物理 ROB。
- **commit**：每个上下文内部按序独立提交；Sniper 的 commit 宽度是**每个上下文一份**，改进 ChampSim2 时要自己定「核级总退休预算」。
- Sniper 是「时序模型参考」，**不是要照抄的规格**。

💡理解：Sniper（另一个模拟器）里有现成的 SMT，同事把它当「参考样例」读。关键收获是一张「**哪些东西每个线程各一份、哪些共享**」的清单——这正是你后面判断「PRF 该不该对半分」用的。同时警告：Sniper 有些账算得糊（issue/commit 预算被每个线程重复算），别照搬。

### Scarab：有用的流水线拆解，但不是 SMT

**原文**：README 明说「无 SMT」。线程/状态按核分配，`NUM_BPS` 不是 SMT 上下文。它的 `Thread_Data`、逐操作所有权、依赖唤醒、阶段局部恢复，是定义 ChampSim2「上下文边界」的好例子，但**不是硬件线程仲裁的证据**。它的地址分离用「core-ID 编码」，别把这个抄进 ChampSim2，显式的地址空间 ID 更清晰。

💡理解：Scarab 这模拟器**根本没做 SMT**，同事如实记录了这个「没有」——不许把它当 SMT 样例套。它唯一有用的是「每线程状态该怎么拆」的参考，以及一个反面教材（它靠「核编号」隐式区分地址，容易混，别学）。

## ChampSim2 里被侦察暴露的改动点（大表，12 行）

💡理解：这是全文最干的精华——**「要加 SMT，ChampSim2 得改哪些地方」**。一行一个，逐条翻成人话：

| 领域 | 现状 | SMT 要改 |
|---|---|---|
| **拓扑和输入** | `main.cc` 要 NUM_CPUS 条 trace；`do_cycle` 给每核填一个输入队列 | trace 数要对齐「硬件上下文」，物理核和 cache 连线保持独立 |
| **流水线所有权** | 一个 `O3_CPU` 拥有一套前端队列、ROB、LSQ、分配器 | 抽出「上下文状态」，保留一个核的 `operate()` 和时钟 |
| **依赖和寄存器** | `RegisterAllocator` 把前后端 RAT、PRF、空闲表揉在一起 | 每个上下文自己一份 RAT，物理总容量要显式限量 |
| **程序顺序** | `program_ordered` 比标量 ID；tracereader 已给全局唯一 ID | 保留唯一 ID 当「对账凭证」；区分「上下文内顺序」和「上下文间仲裁」 |
| **退休和存储** | `retire_rob` 退一个完成前缀；`ROB.front()` 当 store 退休边界 | 每个上下文自己的「按序前线」；一个兄弟卡住不能拖全局顺序 |
| **store 转发** | 按虚拟地址 + 指令顺序匹配 store | 独立上下文即使虚拟地址相同，**绝不能互相转发** |
| **load 完成** | 按返回的虚拟块匹配已发出的 load | 响应要认得「真正等它的人」；VA 相同不等于同一上下文 |
| **地址翻译** | `vmem` 按 `cpu_num` 当键；`finish_translation` 按虚拟页匹配 | 把「CPU=地址空间」这种偶然等价彻底拆开 |
| **请求和响应** | `channel` 请求带 `cpu` 和小 asid；**响应不带**上下文字段 | 光在请求加线程标签不够，回程也得安全 |
| **预测器/BTB** | 无上下文的 hook；ITTAGE 有 static 状态、直接读 `input_queue` | 隔离历史/RAS；审计适配器，传上下文局部的后继信息 |
| **模块守卫** | `require_single_core` 只拒绝非零核 ID | 核 0 上的两个上下文能混过去；要显式校验 SMT 能力 |
| **阶段和输出** | `do_phase` 按 CPU 跟踪完成、任意 EOF 结束 | 定义每上下文进度、共同区间、EOF 行为、分离的统计 |

（另加一条警告：v2 trace 带物理地址，但核心用虚拟地址翻译；加 SMT 时别悄悄切到记录好的物理地址，多条 trace 的物理地址可能重叠。）

## 推荐的最初架构

**原文**：每物理核保留一个 `O3_CPU`，内部显式引入一组「硬件上下文」。核数还是编译期定、cache 拓扑不变；上下文数量可以是运行时属性。最初支持「一核两上下文」，同时保留「一上下文」模式。

然后是一张「谁拥有什么」的表（14 行）+ 策略 + 三个方案：

- **固定配额**（先简单实现，别让容量随线程数翻倍）；动态共享以后再说。
- **三个身份要分开**：物理核 / 硬件上下文 / 地址空间。指令 token 全局唯一；程序顺序只在上下文内部保留。
- **复用 Sniper 的「轮转、每拍一个上下文发射」到 fetch 和 dispatch**。

三个方案对比：
1. **扩展 `O3_CPU`，加显式上下文 + 公共仲裁器 —— 推荐**（契合现有 cache/时钟/核 ID）。
2. 用包装器组合多个 `O3_CPU` —— 复用代码多，但容量重复、时钟/阶段不一致，要侵入式协调。
3. 单独写一个 SMT 核 —— 隔离原型快，但重复流水线、以后会分叉，留作一次性实验。

💡理解：核心结论是**「方案 1：一个核内塞多个'线程槽'」**。关键原则你要记住两条：(1) **物理核、线程槽、地址空间是三样不同的东西，别混**；(2) **资源先固定切成配额**（简单、不翻倍），动态共享以后再做。

## 多阶段开发路线图

### Stage 0 — 侦察（就是这份文档）
产出：带源码链接的侦察报告、所有权对比、影响地图、本路线图。如记录 Scarab 无 SMT，别把它每核循环当 SMT。

### Stage 1 — 身份与上下文抽取，保持「单上下文兼容」
**产出**：`O3_CPU` 仍跑一个上下文，但架构状态显式归这个上下文所有。拆开「物理核/上下文/地址空间」和 trace→上下文映射契约。把上下文状态抽到一个专注单元（候选 `inc/core_context.h`），保持阶段顺序和性能不变。
**退出证据**：现有测试全过；单上下文 trace 结果与基线一致（周期、退休指令、分支数、内存/缓存事件全对）。

💡理解：**「先动结构、不改行为」**——就是在不改变任何结果的前提下，把「属于单个线程的那坨状态」装进一个盒子。做完之后，模拟器跑出来跟现在一模一样，但代码已经为 SMT 铺好路了。

### Stage 2 — 内存命名空间和模块隔离
**产出**：能安全表示两个独立地址空间（虽然还只能单上下文跑）。把上下文/地址空间身份带过请求、cache 合并、翻译、回复。store 转发只在同上下文；load 靠显式等待者完成。
**退出证据**：两个伪造上下文用相同的 VA/IP，能翻译到不同的地方、不会错误合并 TLB 请求、共享 DIB、转发 store、或互相完成 load。

💡理解：**「两家人搬进一栋楼，各自门牌不能串」**——先让系统在逻辑上能分清两个程序（即使它们用的是同样的地址数字），但还不让它们真的一起跑。

### Stage 3 — 一个共享核，两个可运行上下文
**产出**：两个指令流在同一核测试夹具里跑，固定 ROB/LQ/SQ/PRF 配额，独立依赖链，共享阶段预算。轮转前端选择、公平调度遍历、同时发多个就绪的、上下文局部暂停、独立按序退休。
**退出证据**：总量不超过每个宽度/容量；同寄存器指令流互不干涉；A 的 miss/误预测不让 B 停下；A 没退休的 store 不能被 B 当退休处理。

💡理解：**这一步才是 SMT 真正「跑起来」**——两条 trace 真的同时挤进一个核，而且验证「你卡你的、我干我的，互不拖累」。

### Stage 4 — trace 执行、阶段、统计、第一个可交付里程碑
**产出**：两条独立 trace 通过正常命令行在一个核上跑。加运行时上下文数选项（候选 `ooo_cpu.cpu0.threads = 2`）。统计改成每上下文 + 核汇总。定义测量的「共同区间」。
**退出证据**：各种边界（trace 数不对、配额不对、空/短/不等长 trace、早退、EOF、重放）都确定性；每上下文退休数和 IPC、核汇总 IPC、占用/暂停/仲裁计数器都出来。

💡理解：**从「测试夹具」升级到「真命令行能跑、能出漂亮的统计报告」**——这一步做完，才算有一个「能用」的 SMT 基准。

### Stage 5 — 共享策略 + 为研究用的验证
**产出**：一个个往上加策略：动态共享 ROB/寄存器、主动回收配额、别的取指策略、显式预测器表共享。保留固定分配当可复现的参照。
**退出证据**：多种配对的对比（计算/计算、计算/内存等）、加权加速比、每线程 slowdown、无饥饿。

💡理解：到这里才回到你最初纠结的**「PRF 到底对半分还是共享」**——答案是先共享、留固定分配当参照，用数据说话。

### Stage 6 — 更大的拓扑，然后单独的「协作线程」项目
多物理核、多个上下文泛化。协作线程（trace 同步事件、共享地址映射、原子操作/栅栏、内存序）是一个**额外的大设计**，现在就把身份分清楚，别以后回头改核 ID。

💡理解：**从「两家人各干各的」到「两家人合作办公」是另一座山**，明确划到后面单独做。

## 实现前要先冻结的决策（5 个）

1. 固定配额、余数处理、两上下文最小的 PRF 容量。
2. 资格、轮转优先级、哪些阶段能一周期服务多上下文。
3. 预测器容量账 + 初始支持的模块集。
4. 热身/ROI/重放/EOF/未完成请求的精确策略。
5. 保真度：保留 ChampSim2 现有抽象调度/执行模型，还是另做端口/FU 模型。

💡理解：这 5 个决策是「动工前必须拍板」的。**注意第 1 条「PRF 怎么分」和第 2 条「仲裁」——正是 critique 说「不能靠读代码、必须先跑数据」的那两条**。你现在扫资源，就是在给第 1 条供数据。
